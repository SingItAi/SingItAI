# October 11 authentication and wallet release

Baseline: `e47cb33ba3f63e1ff8ceb564d238cb688867f574` in SingItAI. Commit/PR for
these fixes: not yet created. The original review and first remediation are in
[the audit report](2026-10-11-auth-wallet-review.md).

## Included changes

- A1–A4 and A8: atomic Solana budgets, account-bound browser sessions, explicit
  network selection/sign-in, thrown SDK switch failures and read-only recovery
  of uncertain SOL funding.
- A6: Solana allowance directory `0700`, database and SQLite sidecars `0600`.
  Files are created privately and existing permissions are repaired; symlink
  state paths are refused.
- A7: new Base ciphertext authenticates format version, owner, chain, address
  and key. Decryption checks the derived address. Legacy bare keys are validated
  and re-encrypted with the same key/address, using compare-and-swap for concurrent
  readers. No wallet rotation occurs. Validation cannot retrospectively detect
  a legacy row whose address and key were both substituted before owner binding;
  compare trusted historical addresses if such tampering is suspected.
- A9: negative, signed, duplicate and ambiguous content lengths are rejected
  before reading. Transfer encodings are unsupported and rejected. Incomplete
  bodies fail, body reads have a 15-second absolute deadline (including trickling
  data), and sockets have a read timeout. Ordinary JSON requests still work.

A5's setup text is deferred at the owner's explicit request. This release does
not add a Solana on-chain daily limiter.

four subsequent migration/installer tests also passed. All five offline audit

## Apply

From the owner's terminal:

```sh
ssh -t <DEPLOY_USER>@<PROD_HOST> 'sudo \
  SIGN402_APP_ROOT=<APP_CHECKOUT> \
  SIGN402_DEPLOY_USER=<DEPLOY_USER> \
  SIGN402_GATEWAY_ENV=<GATEWAY_ENV> \
  SIGN402_BACKUP_ROOT=<BACKUP_ROOT> \
  SIGN402_STATE_DIR=<STATE_DIR> \
  python3 <RELEASE_DIR>/scripts/apply-auth-wallet-release.py --apply'
```

Enter sudo credentials only in the SSH terminal. The agent's SSH identity does
not have unattended sudo, so it cannot perform this step itself.

The installer refuses a changed production revision or dirty checkout. It checks
release hashes, verifies a copy of the wallet database, stops gateway/web/watcher,
and creates a root-owned `0700` backup in
`<BACKUP_ROOT>/<UTC>-auth-wallet-release`. The backup includes the
state directory, available repository runtime state, configuration, systemd
units, previous changed source files and the release manifest. It then installs
the matched frontend/Python/Solana files, validates and binds all existing Base
wallets, and restarts the services. Local page and unauthenticated session checks
must pass before a success receipt is written. No merchant or payment endpoint
is called.

If the production checkout changes before this command, rebuild and verify the
release instead of overriding the guard. If anything fails after installation
starts, services are stopped for investigation and the backup is retained.

## Recovery considerations

Do not simply revert `user_wallets.py`: the original decrypter does not understand
the new bound envelope. Prefer a forward repair retaining the new decrypter. A
full rollback of code and private state is appropriate only while services remain
stopped and it is established that no later wallet, authorization or payment
records will be lost. Never overwrite a database containing newer activity with
the pre-release backup. No automatic downgrade or payment retry is performed.
